## 1. System Overview

The **Evaluation Pipeline** is a multi-stage AI system that assesses user-submitted work against project rubrics generated by the milestone pipeline. It takes a submission (code, document, or mixed) and produces a structured evaluation report with scores, evidence citations, and actionable feedback.

### What It Produces

Given a submission + rubric criteria, the pipeline generates:

- **Quick Scan Triage** — rapid pass/flag/fail classification with confidence score
- **Fail Feedback** — actionable improvement guidance for verified failures (short-circuit)
- **Per-Deliverable Evaluations** — dimension-scored assessments with evidence citations
- **Judge Validation** — cross-evaluator consistency check with bias detection
- **Synthesized Summary** — narrative strengths, improvements, skill matching, hiring signals
- **Tier-Filtered Report** — viewer-appropriate output (what you pay for = what you see)

### Architecture Pattern

```
┌─────────────────────────────────────────────────────────────────┐
│                      EvaluationService                          │
│   (HTTP adapter: auth, BOLA, tier resolution, report filter)    │
└──────────────────────────┬──────────────────────────────────────┘
                           │
              ┌────────────▼────────────┐
              │  EvaluationOrchestrator  │
              │  (6-stage coordination   │
              │   v1 legacy + v2 new)    │
              └────────────┬────────────┘
                           │
    ┌──────────────────────┼──────────────────────┐
    │    Stage 1           │    Stage 2            │
    ▼                      ▼                      │
  Quick Scan ──→ Trigger Decision                 │
  (LLM triage)   (pure Python)                    │
    │                      │                      │
    │ fail_verified?       │ should_trigger?       │
    ▼                      ▼                      │
  Short-Circuit     ┌─────▼──────┐                │
  (fail feedback)   │   Stage 3  │                │
                    │  Content   │                │
                    │  Router    │                │
                    │ (no LLM)   │                │
                    └──────┬─────┘                │
                           │                      │
                    ┌──────▼──────┐                │
                    │   Stage 4   │                │
                    │  Fan-Out    │     ← parallel │
                    │  Evaluators │                │
                    │  (LLM×N)   │                │
                    └──────┬─────┘                │
                           │                      │
                    ┌──────▼──────┐                │
                    │   Stage 5   │                │
                    │   Judge     │                │
                    │  (LLM)     │                │
                    └──────┬─────┘                │
                           │                      │
              ┌────────────▼────────────┐         │
              │       Stage 6           │         │
              │  6a: Aggregator (math)  │         │
              │  6b: Synthesizer (LLM)  │         │
              │  6c: ReportBuilder      │         │
              └────────────┬────────────┘         │
                           │                      │
                           ▼                      │
                    EvaluationReport               │
                    (tier-filtered)                │
```

**This IS a DAG.** Unlike the milestone pipeline (strict sequential), the evaluation pipeline has:
- A **fan-out stage** (Stage 4) where N evaluators run in parallel via `asyncio.gather`
- A **short-circuit path** for verified failures that bypasses Stages 3-6
- A **conditional path** — if the deep dive trigger says "no," only quick scan runs

### Design Philosophy

The pipeline follows three key patterns:

| Pattern | Components | Purpose |
|---------|-----------|---------|
| **Triage → Deep Dive** | QuickScan → Trigger → Evaluators | Conserve LLM tokens: only worthy submissions get expensive evaluation |
| **Evaluate → Validate** | Evaluators → Judge | Generator → Critic: the Judge never creates content, only validates |
| **LLM → Pure Python** | Synthesizer → Aggregator → ReportBuilder | Only use LLM for what requires language understanding; math and filtering are deterministic |

#### Temperature Strategy

Unlike the milestone pipeline's hot/cold generator-critic pattern, evaluation agents use **uniformly low temperatures** for scoring consistency:

| Agent | Temperature | Rationale |
|-------|------------|-----------|
| QuickScanAgent | 0.2 | Consistent triage decisions; must produce same bucket for same submission |
| CodeEvaluatorAgent | 0.3 | Slightly warmer for nuanced technical judgment |
| DocumentEvaluatorAgent | 0.3 | Same as code evaluator — balanced scoring |
| JudgeAgent | 0.2 | Cold and conservative — validates, never generates |
| FeedbackSynthesizerAgent | 0.4 | Warmest — generates narrative prose, not scores |

The **synthesizer is intentionally warmest** (0.4) because it generates human-readable narrative text where variety improves readability. Scores are set by the aggregator (pure math), not the synthesizer — so the warm temperature cannot inflate or deflate scores.

## 3. Execution Flow — The Dual Pipeline

The orchestrator supports two pipeline versions. The **v2 pipeline** is the current standard; v1 exists for backward compatibility.

### Version Detection

```python
# orchestrator.py:188 — v2 activates when structured inputs are provided
use_v2 = bool(file_list and rubric_criteria_list)
```

### v2 Pipeline: Full 6-Stage Flow

```
EvaluationOrchestrator.run(submission_id, submission_content, ...)
│
├── A. STATE INITIALIZATION
│   ├── Fresh run: EvaluationState(state_id=uuid4(), status="in_progress")
│   └── Resume: EvaluationState.from_dict(initial_state)
│
├── B. AGENT CREATION (lazy, receives user_tier for model selection)
│   ├── QuickScanAgent(user_tier="pro")
│   ├── CodeEvaluatorAgent(user_tier="pro")
│   ├── DocumentEvaluatorAgent(user_tier="pro")
│   └── FeedbackSynthesizerAgent(user_tier="pro")
│
├── Stage 1: QUICK SCAN (if not already complete)
│   │ QuickScanAgent.run(submission_input)
│   │ → QuickScanResult { triage_bucket, confidence, preliminary_score }
│   │ → state.mark_quick_scan_complete(result)
│   │ → checkpoint("QUICK_SCAN_COMPLETE")
│   │
│   └── Stage 1b: FAIL VERIFICATION (if triage == "fail")
│       │ Second LLM pass to prevent false negatives
│       ├── fail_verified=True  → state.mark_fail_verified(fail_feedback)
│       │                       → _finalize_evaluation() → RETURN EARLY
│       └── fail_verified=False → reclassify to "flag", continue
│
├── Stage 2: TRIGGER DECISION (pure Python, no LLM)
│   │ DeepDiveTrigger.should_trigger(TriggerContext)
│   │ Decision tree:
│   │   1. force_deep_dive? → YES (reason: forced)
│   │   2. verified FAIL? → NO (short-circuit)
│   │   3. score >= 70? → YES (reason: score_qualified)
│   │   4. triage == PASS? → YES (reason: score_qualified)
│   │   5. PRO/BUSINESS user? → YES (reason: paid_user)
│   │   6. post-deadline top 10%? → YES (reason: top_n_percent)
│   │   7. else → NO
│   └── If NO trigger → _finalize_evaluation() → RETURN (quick scan only)
│
├── Stage 3: CONTENT ROUTER (pure Python, no LLM)
│   │ ContentRouter.route(file_list, deliverables, criteria)
│   │ → ContentRoutingPlan { deliverable_mappings, unmatched_files, warnings }
│   │ → state.mark_content_routing_complete(plan)
│   │ → checkpoint("CONTENT_ROUTING_COMPLETE")
│   │
│   │ Classification priority:
│   │   1. File extension → ContentType (CODE/DOCUMENT)
│   │   2. MIME type fallback
│   │   3. UNKNOWN → skip (logged as warning)
│   │
│   └── Each mapping: { file_path, content_type, target_evaluator, criterion_id }
│
├── Stage 4: FAN-OUT EVALUATORS (parallel via asyncio.gather)
│   │ For each mapping in routing_plan:
│   │   ├── ContentType.CODE → CodeEvaluatorAgent.run_per_deliverable(...)
│   │   └── ContentType.DOCUMENT → DocumentEvaluatorAgent.run_per_deliverable(...)
│   │
│   │ All run concurrently. Individual failures are logged but don't
│   │ abort the pipeline — surviving evaluations continue.
│   │
│   │ → List[DeliverableEvaluation] with dimension_scores, evidence
│   │ → state.mark_evaluators_complete()
│   │ → checkpoint("EVALUATORS_COMPLETE")
│   │
│   └── If ALL evaluators fail → state.mark_failed() → RETURN
│
├── Stage 5: JUDGE (validation, not generation)
│   │ JudgeAgent.run(evaluator_outputs, rubric_criteria, depth_config)
│   │ → JudgmentResult { verdict, scoring_adjustments, bias_flags }
│   │ → _enforce_adjustment_caps(±15 points max)
│   │ → state.mark_judge_complete(result)
│   │
│   │ Verdicts:
│   │   ├── "approve" → continue to synthesis
│   │   ├── "adjust" → apply score adjustments, continue
│   │   ├── "flag" → mark for human review, continue
│   │   └── "re_evaluate" → retry Stage 4 evaluators once, re-judge
│   │
│   └── checkpoint("JUDGE_COMPLETE")
│
├── Stage 6: SYNTHESIS (three sub-stages)
│   │
│   ├── 6a: AGGREGATION (pure Python)
│   │   SynthesizerAggregator.aggregate(evaluations, judge_result)
│   │   → AggregatedScores { overall_score, per_criterion_scores }
│   │   → Applies Judge adjustments to affected criteria
│   │   → Multiple deliverables per criterion → averaged
│   │
│   ├── 6b: LLM SYNTHESIS
│   │   FeedbackSynthesizerAgent.synthesize(evaluations, scores, depth_config)
│   │   → BriefSummary { strengths, improvements, skill_match, signals }
│   │   → per_criterion_scores overridden with aggregated values (LLM can't change scores)
│   │
│   └── 6c: REPORT BUILDING (pure Python)
│       ReportBuilder.build_report(aggregated, quick_scan, evals, judge, summary)
│       → EvaluationReport { quick_scan, brief_summary, deep_dive }
│       → state.mark_synthesis_complete(report)
│       → checkpoint("SYNTHESIS_COMPLETE")
│
└── FINALIZE
    state.mark_completed()
    return state.to_dict()
```

### v1 Pipeline: Legacy Flow

```
Quick Scan → Trigger → Code/Doc Evaluator → Feedback Synthesizer
```

The v1 pipeline uses holistic evaluation (entire submission at once) rather than per-deliverable evaluation. It produces `SynthesizedFeedback` instead of `EvaluationReport`. It exists for backward compatibility when `file_list` and `rubric_criteria_list` are not provided.

### Key Execution Invariants

1. **Quick Scan runs for every submission** — it is the universal entry point, regardless of tier or pipeline version.
2. **Fail verification is conservative** — a FAIL that can't be verified becomes a FLAG (never a PASS). If verification itself fails, the FAIL is kept but marked `fail_verified=False`.
3. **The Judge never creates content** — it validates, adjusts (±15 max), and flags. It cannot introduce new evidence or dimensions.
4. **Score authority chain**: Evaluators produce raw scores → Judge adjusts → Aggregator computes weighted totals → Synthesizer generates narrative text (but cannot change scores). The `per_criterion_scores` from the aggregator are force-set on the BriefSummary output: `result.per_criterion_scores = per_criterion_scores`.
5. **Individual evaluator failures are non-fatal** — if 3 of 5 evaluators succeed, the pipeline continues with those 3 results. Only total evaluator failure aborts.

## 4. Shared State: The Central Ledger

`EvaluationState` (Pydantic `BaseModel`) is the single source of truth for an evaluation run. The orchestrator reads and writes state exclusively through dedicated transition methods.

### State Lifecycle

```
                          INITIAL
                             │
                    mark_quick_scan_complete()
                             │
                     QUICK_SCAN_COMPLETE ──── [fail_verified?] ──→ FAIL_VERIFIED → COMPLETED
                             │
                   trigger_deep_dive()
                             │
                    DEEP_DIVE_STARTED
                             │
               mark_content_routing_complete()
                             │
                  CONTENT_ROUTING_COMPLETE
                             │
               mark_evaluators_complete()
                             │
                   EVALUATORS_COMPLETE
                             │
                 mark_judge_complete()
                             │
                     JUDGE_COMPLETE
                             │
                mark_synthesis_complete()
                             │
                   SYNTHESIS_COMPLETE
                             │
                    mark_completed()
                             │
                        COMPLETED
```

### State Transition Contract

Each `mark_*` method follows the same pattern:

```python
def mark_<stage>_complete(self, output: Dict[str, Any]) -> None:
    self.<output_field> = output                    # Store agent output
    self.evaluation_stage = "<STAGE>_COMPLETE"      # Advance stage
    self.create_checkpoint("<STAGE>_COMPLETE")       # Recovery point
```

This consistency means the orchestrator never directly sets `evaluation_stage` or calls `create_checkpoint` — the state manages its own invariants.

### Why Dicts Instead of Typed Models?

Agent outputs are stored as `Dict[str, Any]` (not Pydantic model instances) for three reasons:

1. **JSON serialization** — state must be persistable to database. `model_dump(mode='json')` is called once at storage time, not for every field access.
2. **Schema evolution** — if `QuickScanResult` gains a new field, old stored states still deserialize without breaking.
3. **Cross-version compatibility** — v1 and v2 pipelines store different output shapes in the same state object.

## 5. Base Agent Contract

All LLM-calling agents inherit from `BaseEvaluationAgent` (`base.py`). This is a separate class from the milestone pipeline's `BasePipelineAgent` — they share no inheritance but follow similar patterns.

### Core API

```python
class BaseEvaluationAgent:
    # All agents share this interface:

    async def call(system_prompt, user_prompt, response_model=None) -> Any
        # Single LLM call with timeout wrapper + JSON parsing
        # Returns: Pydantic model instance (if response_model) or raw string

    async def call_with_retry(system_prompt, user_prompt, response_model=None, max_retries=2) -> Any
        # Wraps call() with exponential backoff
        # Retries: LLMProviderError, TimeoutError
        # No retry: StructuredOutputError (indicates model misconfiguration)

    def to_json(data) -> str           # Serialize with UUID/datetime handling
    def format_input(label, data) -> str  # "Label:\n{json}"
    def format_section(title, content) -> str  # "## Title\n\ncontent\n"
```

### LLM Call Path

```
call_with_retry()
  └→ call()
      └→ asyncio.wait_for(timeout=self.timeout_seconds)
          └→ _call_llm_with_json(system_prompt, user_prompt)
              ├→ Model selection via LLM Orchestrator (if task_type set)
              ├→ llm_provider.call(response_format="json_object")
              └→ _extract_json_from_text(response)
                  └→ Strip markdown code blocks, find {…} in text
      └→ _parse_structured_output(json_str, response_model)
          └→ Pydantic model(**json.loads(json_str))
          └→ Handle nested wrappers: {"quick_scan_result": {...}} → unwrap
```

### Key Differences from Milestone Pipeline's BasePipelineAgent

| Feature | Milestone BasePipelineAgent | Evaluation BaseEvaluationAgent |
|---------|---------------------------|-------------------------------|
| Thinking mode | Used for milestone planner | Not used (scoring consistency > exploration) |
| Temperature | 0.1-0.5 (hot/cold pattern) | 0.2-0.4 (uniformly low) |
| Timeout default | 120s | 60s (latency-optimized) |
| Retry on parse fail | Yes (retries all errors) | No (StructuredOutputError not retried) |
| State mutation | Agents write to PipelineState directly | Agents return results; orchestrator writes to state |
| Context caching | Not used (one-shot pipeline) | ContextCacheManager for cross-submission reuse |

### Error Hierarchy

```
EvaluationAgentError (base)
├── StructuredOutputError     # JSON parse or Pydantic validation fail — NOT retried
├── EvaluationTimeoutError    # asyncio.wait_for exceeded — retried
└── (LLMProviderError)        # From llm_provider.py — retried
```

The no-retry policy for `StructuredOutputError` is deliberate: if the LLM consistently produces invalid JSON for a given prompt, retrying the same prompt will produce the same bad output. The caller should fix the prompt, not retry.

## 6. Agent-by-Agent Specification

### Agent 1: QuickScanAgent

**File**: `agents/quick_scan.py` | **Prompt**: `quick_scan_prompt.md`

**Role**: Universal triage agent. Runs for every submission. Determines whether the submission warrants expensive deep evaluation.

| Property | Value |
|----------|-------|
| Temperature | 0.2 |
| Max Tokens | 1000 |
| Timeout | 60s |
| Task Type | `submission_evaluation` |
| LLM Calls | 1 (triage) + 1 if fail verification needed |

**Input**: `QuickScanInput` — submission content, project context, rubric criteria, milestone context

**Output**: `QuickScanResult` — triage_bucket (pass/flag/fail), confidence (0-1), preliminary_score (0-100), quick_summary, and optionally fail_verified + FailFeedback

**Triage Logic**:
- **PASS**: Required deliverables present, core criteria addressed, acceptable quality
- **FLAG**: Most deliverables present with concerns, partially addressed criteria, mixed signals
- **FAIL**: Major deliverables missing, core criteria unaddressed, fundamental gaps

**Fail Verification (two-pass safety net)**:

When the initial triage returns FAIL, the agent automatically runs a second LLM pass to prevent false negatives. This is critical because a false FAIL costs the enterprise a potentially good candidate.

```
Initial triage = FAIL
  └→ _verify_and_enrich_fail()
      └→ Second LLM call with different system prompt
          ├── confirmed=True  → FAIL kept, FailFeedback generated
          │   FailFeedback: { missing_criteria, specific_gaps, actionable_suggestions }
          └── confirmed=False → Reclassified to FLAG
              Quick summary appended: "[Reclassified: needs deeper review]"
```

If the verification call itself fails (LLM error), the conservative choice is to keep the FAIL but mark `fail_verified=False`. The submission can still be re-evaluated manually.

**Prompt Design**: The prompt includes an explicit bias mitigation checklist:
- Technology neutrality enforcement
- Experience calibration rules
- Partial credit mandate
- Cultural neutrality

### Agent 2: ContentRouter

**File**: `agents/content_router.py` | **Prompt**: None (pure Python)

**Role**: Deterministic file classifier. Maps each submission file to the appropriate evaluator agent based on file extension. **No LLM calls.**

| Property | Value |
|----------|-------|
| Temperature | N/A |
| Max Tokens | N/A |
| Timeout | N/A (instant) |
| LLM Calls | 0 |

**Input**: File list, deliverable definitions, rubric criteria, optional MIME types

**Output**: `ContentRoutingPlan` — deliverable_mappings, unmatched_files, routing_warnings

**Classification Priority**:
1. **Special filenames** (Dockerfile, Makefile, README → CODE or DOCUMENT)
2. **File extension** (.py → CODE, .md → DOCUMENT — ~60 extensions mapped)
3. **MIME type fallback** (text/x-python → CODE)
4. **UNKNOWN** → added to `unmatched_files` with warning

**Criterion Matching**: Each file is matched to the most relevant rubric criterion using `deliverable_type` matching:
- Code files match criteria with `deliverable_type` of "code" or "any"
- Document files match criteria with `deliverable_type` of "document" or "any"
- Returns the **first** matching criterion — this is a known limitation (see Section 14)

**Why No LLM?** File type classification is a solved problem that doesn't benefit from language understanding. Using extension-based classification is:
- **Deterministic** — same file always routes to same evaluator
- **Fast** — instant, no latency
- **Free** — no token cost
- **Testable** — pure function, easy to unit test

### Agent 3: CodeEvaluatorAgent

**File**: `agents/code_evaluator.py` | **Prompt**: `code_evaluator_prompt.md`

**Role**: Deep technical evaluation of code submissions against rubric criteria with evidence-backed dimension scoring.

| Property | Value |
|----------|-------|
| Temperature | 0.3 |
| Max Tokens | 2500 (tier-adjustable via DepthConfig) |
| Timeout | 90s |
| Task Type | `milestone_review` |
| LLM Calls | 1 per deliverable |

**Two Evaluation Modes**:
- **Holistic** (v1 legacy): `run()` — entire submission → `CodeEvaluationResult`
- **Per-deliverable** (v2): `run_per_deliverable()` — single file vs one criterion → `DeliverableEvaluation`

**5 Evaluation Dimensions** (fixed weights, sum to 1.0):

| Dimension | Weight | What It Measures |
|-----------|--------|-----------------|
| Technical Correctness | 0.30 | Does the code work as specified? |
| Code Quality | 0.25 | Best practices, maintainability, readability |
| Completeness | 0.25 | All requirements for this criterion addressed? |
| Communication | 0.10 | Documentation, naming, comments |
| Creativity | 0.10 | Novel approaches, elegant solutions |

**Evidence Requirements** (tier-controlled via DepthConfig):
- LAUNCH: 1-2 citations per dimension
- PRO: 2-3 citations per dimension
- BUSINESS: 3-5 citations per dimension

Each citation includes: `location` (file:line), `quote` (brief snippet), `relevance` (why it matters), `type` (strength/improvement)

**Prompt Ordering**: The per-deliverable user prompt follows Tier 1 ordering — rubric criterion appears **before** code content. This ensures the LLM reads evaluation criteria before seeing the submission, reducing anchoring bias.

**Post-LLM Corrections**: After the LLM returns, the agent force-corrects metadata fields that the LLM may have hallucinated:
```python
if result.deliverable_name != deliverable_name:
    updates["deliverable_name"] = deliverable_name
if result.content_type != "code":
    updates["content_type"] = "code"
if result.criterion_id != criterion_id:
    updates["criterion_id"] = criterion_id
```

### Agent 5: JudgeAgent

**File**: `agents/judge.py` | **Prompt**: `judge_prompt.md`

**Role**: Cross-evaluator validation and quality assurance. Sits between evaluators and synthesis. **Never produces evaluation content** — only validates, adjusts, and flags.

| Property | Value |
|----------|-------|
| Temperature | 0.2 (coldest — conservative judgments) |
| Max Tokens | 1200 (tier-adjustable) |
| Timeout | 60s |
| LLM Calls | 1 (+ 1 if re_evaluate verdict triggers retry) |

**Three Validation Checks**:

1. **Evidence Quality** (all tiers): Do citations support scores? Are they specific (file:line) or vague? Enough citations per dimension? Rate 0.0 to 1.0.

2. **Scoring Consistency** (all tiers): Are scores proportional across dimensions? Similar quality evidence → similar scores? Watch for halo effect, central tendency, order effect.

3. **Bias Detection** (BUSINESS tier only): Systematic biases — technology preference, style expectations, experience assumptions, cultural biases. Reported as `BiasFlag` with severity and recommendation.

**Verdicts and Their Effects**:

| Verdict | Effect | When Used |
|---------|--------|-----------|
| `approve` | No changes, proceed to synthesis | Evidence adequate, scores proportional |
| `adjust` | Apply score adjustments (each ±15 max), proceed | 1-3 dimensions need minor correction |
| `flag` | Mark for human review, proceed | Systematic issues, evidence < 0.5, high-severity bias |
| `re_evaluate` | Retry Stage 4 evaluators once, re-judge | Missing dimensions, no evidence, malformed output |

**Adjustment Cap Enforcement** (`_enforce_adjustment_caps`):

This is a critical safety mechanism. The LLM's proposed adjustments are post-processed in pure Python:

```python
MAX_ADJUSTMENT = 15.0  # Hard cap

delta = adj.adjusted_score - adj.original_score
if abs(delta) > MAX_ADJUSTMENT:
    capped_score = original + (±MAX_ADJUSTMENT)
    adj.reason += f" [capped from {delta:+.1f} to ±{MAX_ADJUSTMENT}]"
```

The cap prevents the Judge from overriding evaluator judgment too aggressively. A ±15 point swing can change the triage bucket but can't completely invert a score.

### Agent 6: FeedbackSynthesizerAgent

**File**: `agents/feedback_synthesizer.py` | **Prompt**: `feedback_synthesizer_prompt.md`

**Role**: LLM-powered narrative generation. Produces human-readable summary text from structured evaluation data. **Does not control scores** — scores are set by the SynthesizerAggregator (pure math) and force-set on the output.

| Property | Value |
|----------|-------|
| Temperature | 0.4 (warmest — prose generation) |
| Max Tokens | 2000 (tier-adjustable) |
| Timeout | 60s |
| LLM Calls | 1 |

**Two Entry Points**:
- `synthesize()` — new pipeline (per-deliverable evaluations + aggregated scores → `BriefSummary`)
- `run()` — legacy pipeline (holistic evaluations → `SynthesizedFeedback`)

**Output** (`BriefSummary`):
```python
{
    "per_criterion_scores": {"crit_abc": 78.5},  # FROM AGGREGATOR, not LLM
    "strengths": ["Strength 1 with evidence ref", ...],
    "improvements": ["Area with actionable guidance", ...],
    "skill_match": null | { role_name, match_percentage, matched_skills, gap_skills },
    "enterprise_hiring_signals": null | { recommendation, risk_factors, standout_qualities },
    "individual_growth_tips": null | { top_improvement_area, actionable_steps, estimated_effort },
}
```

**Score Override Safety**: After the LLM returns, the synthesizer's `per_criterion_scores` are replaced with the aggregator's deterministic values:

```python
# orchestrator.py:502 — LLM cannot change scores
result.per_criterion_scores = per_criterion_scores
```

This ensures the LLM generates narrative text (strengths, improvements) but cannot inflate or deflate scores.

### Pure Python Components

These components perform deterministic operations without LLM calls. They exist as separate classes to maintain the principle: **only use LLM for what requires language understanding**.

#### SynthesizerAggregator

**File**: `agents/synthesizer_aggregator.py`

Pure Python score aggregation. Applies Judge adjustments and computes weighted averages.

```python
AggregatedScores = {
    overall_score: float,              # Weighted average of per-criterion scores
    per_criterion_scores: Dict[str, float],  # criterion_id → score
    applied_adjustments: List[ScoringAdjustment],  # Which Judge adjustments were applied
    bias_flags_count: int,             # Count of detected biases
    deliverable_count: int,            # How many deliverables were evaluated
}
```

**Aggregation Logic**:
1. Build adjustment lookup from Judge result: `criterion_id → adjusted_score`
2. For each evaluation, use the adjusted score (if Judge adjusted) or the original `weighted_total`
3. If multiple deliverables map to the same criterion, **average** their scores
4. Overall score = simple average of per-criterion scores, clamped to [0, 100]

#### ReportBuilder

**File**: `agents/synthesizer_report_builder.py`

Pure Python report assembly and tier-based filtering. Two responsibilities:

1. **Build** — assemble `EvaluationReport` from all pipeline stage outputs
2. **Filter** — expose only the sections a given viewer is allowed to see

The filtering is covered in Section 8 (Two-Axis Tier Model).

## 8. The Two-Axis Tier Model

The evaluation pipeline implements a **two-axis tier system** that controls both evaluation depth and report visibility independently.

### Axis 1: Evaluation Depth (DepthConfig)

Controlled by the **enterprise subscription tier** of the project owner. Determines how thoroughly the AI evaluates each submission.

**File**: `schemas/evaluation_pipeline/depth_config.py`

```
┌──────────────────────────────────────────────────────────────────────┐
│                          Evaluation Depth                            │
├──────────┬──────────────┬──────────────┬───────────────────────────────┤
│ Setting  │ LAUNCH       │ PRO          │ BUSINESS                      │
├──────────┼──────────────┼──────────────┼───────────────────────────────┤
│ Citations│ 1-2/dim      │ 2-3/dim      │ 3-5/dim                       │
│ Reasoning│ brief        │ moderate     │ detailed                      │
│ Skills   │ OFF          │ ON           │ ON                            │
│ Bias det.│ OFF          │ OFF          │ ON                            │
│ Ranking  │ OFF          │ OFF          │ ON                            │
│ Tokens   │ 1000/agent   │ 1500/agent   │ 2000/agent                    │
└──────────┴──────────────┴──────────────┴───────────────────────────────┘
```

A single `DepthConfig` instance is created per evaluation run and passed to every agent. Agents read `depth_config.min_citations_per_dimension`, `depth_config.reasoning_depth`, etc. to adjust their prompts and output format.

### Axis 2: Report Visibility (ReportBuilder)

Controlled by the **viewer's type (enterprise/individual) and tier**. Determines which sections of the completed report each user can see.

**File**: `agents/synthesizer_report_builder.py`

```
┌──────────────────────────────────────────────────────────────────────┐
│                        Report Visibility                             │
├────────────────┬────────────┬──────────────┬─────────────────────────┤
│ Viewer         │ LAUNCH     │ PRO          │ BUSINESS                │
├────────────────┼────────────┼──────────────┼─────────────────────────┤
│ Enterprise     │ quick_scan │ + brief_summ │ + deep_dive             │
│ Individual     │ quick_scan │ + brief_summ │ + brief_summ (no dive)  │
└────────────────┴────────────┴──────────────┴─────────────────────────┘

Lens-specific filtering within brief_summary:
  Enterprise viewer → sees hiring_signals, NOT growth_tips
  Individual viewer → sees growth_tips, NOT hiring_signals
```

### Why Two Axes?

A BUSINESS enterprise pays for deep evaluation (Axis 1), producing detailed per-deliverable evidence and bias detection. But an INDIVIDUAL submitter to that same project only sees their relevant sections (Axis 2). The enterprise's investment in evaluation depth benefits them when reviewing candidates — the individual sees growth-oriented feedback appropriate to their tier.

This prevents the awkward scenario where a LAUNCH individual submitter sees BUSINESS-depth evaluation results that reference hiring signals and ranking data.

## 9. Anti-Hallucination & Anti-Bias Strategy

### Anti-Hallucination

**Problem**: LLMs can generate plausible but fabricated evidence, inflate scores, or claim criteria are met when they aren't.

**Countermeasures**:

| Strategy | Implementation | Where |
|----------|---------------|-------|
| **Evidence grounding** | Every score must cite file:line references | Code/Doc evaluator prompts |
| **Score override** | Aggregator's math overrides LLM's scores | `orchestrator.py:502` |
| **Metadata correction** | Agent force-corrects hallucinated metadata | `code_evaluator.py:253-261` |
| **Structured output** | JSON schema validation via Pydantic | `base.py:_parse_structured_output` |
| **Judge validation** | Second LLM checks if evidence supports scores | `judge.py` |
| **Deterministic routing** | No LLM for file classification | `content_router.py` |
| **Adjustment caps** | Judge can't change scores by more than ±15 | `judge.py:_enforce_adjustment_caps` |
| **Fail verification** | Second pass for FAIL triage to catch false negatives | `quick_scan.py:_verify_and_enrich_fail` |

### Anti-Bias

**Problem**: LLMs exhibit systematic biases — favoring certain technologies, writing styles, experience levels, or cultural conventions.

**Countermeasures**:

| Strategy | Implementation | Where |
|----------|---------------|-------|
| **Technology neutrality** | "Any tech stack meeting requirements scores equally" | All evaluator prompts |
| **Experience calibration** | "Judge against rubric expectations, not senior standards" | `quick_scan_prompt.md` |
| **Partial credit mandate** | "60% complete = ~60% score, not automatic fail" | `quick_scan_prompt.md` |
| **Cultural neutrality** | "Code comments in any language are acceptable" | `quick_scan_prompt.md` |
| **Bias checklist** | Self-check before finalizing scores | `quick_scan_prompt.md` |
| **Bias detection** | Judge checks for systematic bias (BUSINESS tier) | `judge.py` |
| **Prompt ordering** | Rubric criteria before submission content | `code_evaluator.py:_build_per_deliverable_user_prompt` |
| **Low temperature** | 0.2-0.3 for scoring consistency | All agents |

### Bias Detection Categories (BUSINESS Tier)

The Judge agent checks for four bias types:

| Bias Type | Example | Detection |
|-----------|---------|-----------|
| Technology | Favoring React over Vue despite rubric allowing any framework | Cross-submission scoring pattern analysis |
| Style | Penalizing functional style when OOP was equally valid | Evidence-vs-score mismatch |
| Anchoring | First impression dominating despite later evidence | Score trajectory analysis |
| Cultural | Assuming Western documentation conventions | Naming/comment language analysis |

Each detected bias is reported as a `BiasFlag` with severity (low/medium/high) and a mitigation recommendation.

## 10. Infrastructure Layer

### Context Cache

**File**: `context_cache.py`

**Problem**: When an enterprise project receives 100 submissions, each evaluation needs the same project context, milestone requirements, and rubric criteria. Rebuilding this context from the database for each submission wastes tokens and adds latency.

**Solution**: In-memory cache with TTL-based expiration, keyed by `project_id:milestone_id:version`.

```
Cache Key: "eval_ctx:{project_id}:{milestone_id}:v{version}"

CachedProjectContext:
  ├── project_context: { title, description, business_goal, constraints, deliverables }
  ├── rubric_criteria: [ { id, name, description, weight, scoring_guide } ]
  ├── milestone_context: { title, requirements, acceptance_criteria }
  └── estimated_tokens: int (for cost budgeting)
```

**Cache Properties**:
- TTL: 1 hour (configurable)
- Max entries: 1000 (LRU eviction when exceeded)
- Thread-safe: `asyncio.Lock` for concurrent access
- Cleanup: Expired entries removed every 5 minutes
- Invalidation: By project (bumps version) or by specific milestone

**Token Estimation**: `estimate_tokens()` uses the 4-chars-per-token heuristic for cost budgeting. Not exact, but sufficient for deciding whether to include scoring guides in prompts.

**Singleton**: `get_context_cache_manager()` returns a module-level singleton. Reset with `reset_context_cache_manager()` in tests.

### Rubric Adapter

**File**: `rubric_adapter.py`

**Problem**: The milestone pipeline produces `EvaluationRubricItem` (criterion text + weight + scoring_method). The evaluation pipeline needs `RubricCriterion` (id + name + description + weight + scoring_guide + deliverable_type). These schemas don't match.

**Solution**: The rubric adapter transforms between formats.

```
Milestone Pipeline Output              Evaluation Pipeline Input
──────────────────────────              ─────────────────────────
EvaluationRubricItem:                   RubricCriterion:
  criterion: str         ──→             id: "crit_a1b2c3d4" (hash-generated)
  weight: float          ──→             name: str[:100]
  scoring_method: str    ──→             description: str
                         ──→             weight: float
                         ──→             scoring_guide: ScoringGuide
                         ──→             deliverable_type: "code"/"document"/"any"
```

**Criterion ID Generation**: `generate_criterion_id()` creates a stable, deterministic ID by hashing `milestone_id:criterion_text`. This means the same criterion always gets the same ID, enabling Judge adjustments to reference specific criteria across evaluation runs.

**Deliverable Type Inference**: `_infer_deliverable_type()` uses keyword heuristics to classify criteria. Code keywords: "implementation", "function", "class", "api", "endpoint", "test". Document keywords: "document", "readme", "spec", "design", "report".

**LLM Formatting**: `format_rubric_for_llm()` converts criteria to a token-efficient markdown format. If the result exceeds `max_tokens`, it recursively retries without scoring guides. If still too long, it truncates with an ellipsis.

### Timeout & Token Calculator

**File**: `timeout_calculator.py`

**Problem**: Fixed timeouts either time out on complex submissions (too short) or waste money on simple ones (too long). Fixed token budgets underserve detailed evaluations and overspend on simple ones.

**Solution**: Adaptive calculation based on input characteristics.

**Timeout Formula**:
```
timeout = (base_timeout + size_factor) × model_mult × complexity_mult

base_timeout: Agent-specific (30-45s)
size_factor:  (input_tokens / 10,000) × 15s
model_mult:   flash=0.7, primary=1.0, thinking=2.5
complexity:   simple=0.7, normal=1.0, complex=1.5

Clamped: 30s ≤ timeout ≤ 300s
```

**Token Budget Formula**:
```
budget = tier_base + scaling_factor × extra_units

tier_base:      LAUNCH=1000, PRO=1500, BUSINESS=2000 (per agent)
scaling_factor: Agent-specific (100-400 tokens per extra unit)
extra_units:    Criteria beyond baseline 5, or deliverables beyond baseline
```

**Per-Agent Base Timeouts**:

| Agent | Base Timeout | Rationale |
|-------|-------------|-----------|
| quick_scan | 30s | Lightweight triage, short output |
| content_router | 2s | No LLM, pure Python |
| code_evaluator | 45s | Deep analysis with evidence |
| document_evaluator | 45s | Same as code |
| judge | 30s | Validates, doesn't generate |
| feedback_synthesizer | 45s | Generates narrative prose |

### Deep Dive Trigger

**File**: `trigger.py`

**Problem**: Not every submission deserves expensive deep evaluation. The trigger decides which submissions get the full pipeline.

**Decision Tree** (evaluated in order):

```
1. force_deep_dive=True?                    → YES (reason: forced)
2. triage_bucket=fail AND fail_verified?     → NO  (short-circuit)
3. preliminary_score >= 70?                  → YES (reason: score_qualified)
4. triage_bucket == "pass"?                  → YES (reason: score_qualified)
5. user_tier in (PRO, BUSINESS)?             → YES (reason: paid_user)
6. post-deadline AND top 10%?                → YES (reason: top_n_percent)
7. else                                      → NO
```

**Notable**: Score threshold (check 3) and pass bucket (check 4) trigger for **all tiers**, including LAUNCH. This means a free-tier user whose submission scores 70+ still gets deep evaluation. The paid_user check (check 5) is a safety net — PRO/BUSINESS users always get deep dive regardless of score.

**Percentile Calculation** (check 6): Only applies post-deadline when `all_submission_scores` is provided. Counts submissions with lower scores, divides by total. Top 10% means percentile rank ≥ 90.

## 11. LLM Infrastructure Layer

The evaluation pipeline shares LLM infrastructure with the milestone pipeline. See `MILESTONE_PIPELINE_ARCHITECTURE.md` Section 12 for full details. Key points specific to evaluation:

### Model Selection

Agents set `task_type` in their constructor, which the `LLMOrchestrator` uses to select appropriate models:

```python
# Quick scan uses "submission_evaluation" → flash model (fast, cheap)
QuickScanAgent(task_type="submission_evaluation")

# Evaluators use "milestone_review" → primary model (capable, balanced)
CodeEvaluatorAgent(task_type="milestone_review")
```

The `user_tier` parameter further refines model selection — BUSINESS users may route to more capable models.

### response_format Constraint

All evaluation agents use `response_format="json_object"`. Per CLAUDE.md gotcha #47, this is **incompatible with thinking mode** on Chinese LLM providers (Qwen, Kimi, ZhipuAI). The `_call_model_by_name()` router in `llm_provider.py` suppresses thinking when `json_object` is present.

This is an intentional tradeoff: **consistent JSON output > reasoning exploration** for evaluation agents. The milestone pipeline makes the opposite choice for its planner agent (thinking > JSON structure).

### Token Budget Flow

```
DepthConfig (enterprise tier)
  └→ timeout_calculator.get_token_budget(agent_name, tier, extra_units)
      └→ BaseEvaluationAgent.__init__(max_tokens=budget)
          └→ llm_provider.call(max_tokens=self.max_tokens)
```

## 12. Persistence and Resume

### Current State: In-Memory Only

`EvaluationState` is held in memory within the `EvaluationOrchestrator` instance. The final state is returned as a `Dict[str, Any]` via `state.to_dict()` and stored in the submission's `ai_analysis` JSONB column by the service layer.

### Resume Capability

The orchestrator supports resuming from a previously stored state:

```python
orchestrator.run(
    submission_id="...",
    initial_state=previous_state_dict,  # Restores from checkpoint
    ...
)
```

The state's `is_quick_scan_complete()` and `is_deep_dive_complete()` methods prevent re-running completed stages. However, resume only works at stage boundaries — there's no intra-stage checkpoint for individual evaluator fan-out.

### Checkpoint Strategy

Each `mark_*_complete()` method calls `create_checkpoint()`:

```
QUICK_SCAN_COMPLETE       ← Can resume from here
CONTENT_ROUTING_COMPLETE  ← Can resume from here
EVALUATORS_COMPLETE       ← Can resume from here (but individual evaluator results are lost)
JUDGE_COMPLETE            ← Can resume from here
SYNTHESIS_COMPLETE        ← Can resume from here
```

## 13. Contrast with Milestone Pipeline

Understanding the differences between the two pipelines helps developers avoid applying patterns from one where they don't belong.

| Dimension | Milestone Pipeline | Evaluation Pipeline |
|-----------|-------------------|---------------------|
| **Topology** | Strict sequential (7 steps) | DAG with fan-out, short-circuit, conditional paths |
| **Fan-out** | None — each agent runs once | Stage 4: N evaluators run in parallel |
| **Short-circuit** | Clarity gate stops pipeline | Verified FAIL bypasses deep dive |
| **Temperature pattern** | Hot/cold (0.5 planner / 0.1 critic) | Uniformly low (0.2-0.4 for all) |
| **State mutation** | Agents write directly to PipelineState | Agents return results; orchestrator writes |
| **Context reuse** | None (one-shot per project) | ContextCacheManager (cross-submission) |
| **Thinking mode** | Used for milestone planner | Not used (json_object incompatible) |
| **Streaming** | SSE via StreamingPipelineRunner | Not supported (batch only) |
| **Assembler** | Pure Python Assembler with cross-validation | Three components: Aggregator + Synthesizer + ReportBuilder |
| **Tier model** | PAYG flag (binary) | Two-axis (DepthConfig × ViewerTier) |
| **Base class** | BasePipelineAgent | BaseEvaluationAgent (separate, no shared inheritance) |
| **Prompt files** | .md in prompts/milestone_pipeline/ | .md in prompts/evaluation_pipeline/ |
| **Validator** | validators.py (shared between orchestrator + streaming) | No validator (Judge agent serves this role) |
| **Pipeline versions** | Single version | v1 (legacy) + v2 (per-deliverable) |

## 14. Known Limitations and Technical Debt

### Active Limitations

1. **No streaming support** — The evaluation pipeline runs in batch mode only. There's no SSE streaming equivalent of `StreamingPipelineRunner`. For long evaluations (>2 min), the client polls for completion.

2. **Single-file content per evaluator** — In `_run_v2_deep_dive`, each evaluator receives the full `submission_content` string, not just the specific file content. When a submission has 10 files, each evaluator processes all 10 files even though it should only evaluate one. This wastes tokens and may confuse the LLM.

3. **First-match criterion routing** — `ContentRouter._match_to_criterion` returns the first criterion matching the file's `deliverable_type`. If a submission has 5 code files and 3 code criteria, all 5 files may map to the first criterion. A more sophisticated matching algorithm (e.g., name similarity, keyword overlap) would distribute files more evenly.

4. **No per-file content extraction** — The `file_list` parameter contains file names, but the actual content of individual files is not separated. The orchestrator passes the entire `submission_content` to each evaluator regardless of which file was routed.

5. **In-memory context cache only** — `ContextCacheManager` is in-memory with a singleton pattern. In a multi-instance deployment (Render with multiple workers), each instance has its own cache. Redis-backed caching would share context across instances.

6. **Token/cost tracking not implemented** — `EvaluationState.tokens_used` and `estimated_cost_usd` fields exist but are never populated. The LLM provider doesn't expose token usage back to the calling agent.

7. **Re-evaluate retry uses stale tasks** — When the Judge returns `re_evaluate`, `orchestrator.py:469` re-runs the same `tasks` list from the initial fan-out. These are the same `asyncio.gather` coroutines, which may have already been consumed. The retry should create fresh coroutine objects.

8. **Aggregation averages duplicates** — `SynthesizerAggregator` averages scores when multiple deliverables map to the same criterion. This is a simple strategy that may not reflect the intended rubric weighting. A weighted approach considering file importance would be more accurate.

9. **No video evaluator** — `ContentType` supports UNKNOWN but not VIDEO. Video submissions are routed to UNKNOWN and skipped. A video evaluator agent is planned but not yet implemented.

10. **improvement_roadmap and skill_gap_analysis not populated** — `DeepDiveReport.improvement_roadmap` and `skill_gap_analysis` are always empty lists/dicts. The ReportBuilder creates them but no pipeline stage populates them. These would require an additional LLM call or deterministic derivation from evaluator outputs.

### Technical Debt

1. **Dual pipeline maintenance** — v1 and v2 codepaths in the orchestrator must be maintained in parallel. The v1 path uses different schemas (`SynthesizedFeedback` vs `EvaluationReport`), different state transitions, and different agent method signatures.

2. **Legacy backward-compat fields** — `orchestrator.py:530-536` manually populates `synthesized_feedback` with v1-format data after v2 pipeline completes, for clients that still read the old field location.

3. **Trigger reason type mismatch** — `EvaluationState.deep_dive_trigger_reason` has Literal type `['score_threshold', 'top_n_percent', 'paid_user']` (missing `score_qualified` and `force`). The trigger can produce these reasons but the state type doesn't accept them without a type: ignore.

4. **Inconsistent task_type usage** — `CodeEvaluatorAgent` uses `task_type="milestone_review"` (not `submission_evaluation`). This routes it to the same model class as milestone reviewers, which may not be ideal for code evaluation workloads.

5. **No dead letter queue** — Failed evaluator outputs are logged but not stored for analysis. A dead letter pattern would help debug systematic evaluator failures without re-running the entire pipeline.
