The Claude Code Playbook for Solving Complex Tasks

Synthesized from docs/superpowers/specs/ (5) and docs/superpowers/plans/ (24). ~45,000 lines across board-hardening, agentic-research, eval-harness, and harness-cross-cutting workstreams, Apr 15 – May 18, 2026.
The corpus shows a remarkably consistent operating discipline: brainstorm → spec → plan → TDD-per-task → PR → verify. Each stage produces a named artifact with a fixed shape. Nothing is ad-hoc; nothing is implicit.

1 Interpret the request

The first decision is what artifact to produce, not what code to write.

Request signalArtifact path
<10 LoC, <3 files, no API changeEdit directly. Skip both spec and plan.
Multi-file feature inside one subsystemPlan only (no spec) — refinements table, file structure, TDD tasks.
Cross-cutting feature, new ABI, multiple subsystemsSpec → plan(s) → PR(s). One spec, often N plans (one per phase).
"Like in OpenHarness…" / "compare X to Y"Brainstorm artifact first (HTML comparison doc), spec second.
"Rebuild Y" / "redesign Z"Multi-phase spec (P1 … P5), each phase its own plan.

Pin upfront, before writing anything

  • Status line. Draft (awaiting user review) or pinned <date>. Never implement from a draft.
  • Goals AND non-goals. Non-goals are load-bearing — they're the contract that prevents scope creep.
  • Companion documents. Link the brainstorm artifact and any assessment doc so the rationale chain survives.
Example 2026-05-18-harness-cross-cutting-expansion-design.md lists 4 explicit goals, 6 non-goals, plus a 7th deferred-with-reason (MCP transport: "no external tool consumer exists; building it speculatively would be scaffolding without callers").

2 Analyze the complexity

2.1 Tier the work

TierTriggerDiscipline
LIGHTTrivial seam, single fileEdit + verify. Skip Pre-Impl §1, §4.
STANDARDMulti-file, single subsystemPlan with refinements + TDD tasks.
HEAVYCross-cutting, new ABISpec + per-phase plan + preconditions gate.

2.2 Find the load-bearing assumption

For every task, ask: "What single decision, if it broke, would invalidate this whole design?"

That decision needs a pinned answer with rationale in the spec — never a future-tense "we'll figure it out." When the spec leaves N decisions open, write a design-choices supplement with a numbered register (DC1, DC2, …) — that's how P5b's auto-promote pinned its 5 open questions and how P4 SOTB pinned DC1–DC6.

2.3 Map the seams in three columns

Created   | File | Purpose
Modified  | File | Change
Untouched | File | Reason  ← the column that prevents scope creep

3.3 The "one module per new concept" rule

SOTB governance got its own server/memory/sotb_governance.py even though server/memory/sotb.py existed. Folding governance into sotb.py would couple six unrelated callers (cli.py, api/routes/memory.py, harness/replay.py, projection.py…) to a new return shape.

Rule When in doubt, a new module beats touching an existing one. Blast radius stays small, test mocks stay clean.

4.2 The preconditions gate

grep -q "auto_promote_enabled" server/harness/config.py \
  && echo "ALREADY PRESENT — stop" \
  || (grep -q "expand_peer_max" server/board/deliberation/orchestrator.py \
      && echo "P5a present, P5b not yet — OK to proceed" \
      || echo "MISSING precursor — stop and wait")
Three outcomes, one command. If MISSING or ALREADY PRESENT, the implementer stops — no partial work, no force-overwriting another branch.

4.3 The optional BRAINSTORM-FIRST GATE

For plans whose design choices have real downside risk (destructive writes, auto-resolution), the plan adds a callout box before the tasks begin:

Example from P4 SOTB "Recommendation: proceed to execution. DC2 (log-only) and DC6 (judge-disabled by default) are conservative pinned choices… However, if the user wants to revisit DC2 or DC3, a short brainstorming pass would be cheap insurance before T1 lands."

5 Task-level TDD loop

Every task — without exception — has the same five steps and commit cadence:

Step 1: Write the failing test
Step 2: Run the failing test (assert specific error message — this IS the contract)
Step 3: Write the minimal implementation (only what the test exercises)
Step 4: Run the test (assert PASS)
Step 5: Commit (HEREDOC commit message + Co-Authored-By footer)

Why Step 2 matters

The "expected error" line is the test's contract. If the actual error differs, the test isn't testing what you think.

Why Step 3 says minimal

YAGNI — no fields the test doesn't exercise. The next test will demand them, with a reason.
One commit per task, not per PR. Each commit is a green-tests checkpoint that can be reverted individually. 
git commit -m "$(cat <<'EOF'
<scope>(<phase>): <short imperative sentence>

<paragraph: what changed and why; reference spec § if relevant>

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"

6 Tool-calling patterns

6.1 The pre/post-hook contract

@dataclass(frozen=True)
class HookContext:
    tool_name: str
    stage: int
    session_id: str
    member_id: str | None
    request: dict          # read-only by convention

@dataclass(frozen=True)
class HookVerdict:
    action: Literal["allow", "deny"]
    reason: str | None     # required when deny
    metadata: dict         # logged to ledger

6.2 Dispatch semantics — all pinned, no implementer choice

RuleCode shape
Pre-hooks fire in registration orderList append, iterate in order
First deny short-circuitsif v.action == "deny": return v
All-allow merges metadata{**v1.metadata, **v2.metadata} — last writer wins, documented
Post-hooks all fire, log-not-raiseWrap each in try/except, logging.exception
Hook crash → denyHookVerdict("deny", reason=f"hook crashed: {type(exc).__name__}", metadata={})
Hook timeout → denyasyncio.wait_for(..., timeout=5.0) → TimeoutError → deny
Async/sync coercionif inspect.isawaitable(r): r = await asyncio.wait_for(r, 5.0)

6.3 What tools may NOT do in V1

  • Mutate the request or the result (observe + block only).
  • Maintain in-process counters (read from hook_events table — restart-safe).
  • Configure their own timeout (single _HOOK_TIMEOUT_SECONDS = 5.0 constant).
  • Auto-discover (members declare; system doesn't infer).

6.4 The agentic tool-use loop pattern

  • Wrap, don't replace. agentic_member_turn wraps query_llm; the legacy single-call path stays for fast-mode.
  • Budget every loop. ToolBudget per stage per member; sub-caps per tool.
  • Tool registry shape. (name, description, parameters_schema, handler) — provider-agnostic JSON schema.
  • One new ABI seam. LLMResponse.tool_calls, query_llm(tools=, tool_choice=). Every provider adapter handles translation.

Auto-discover or registered?Registered. _bundled/ ships, _project/ gitignored.

Subagent execution rule (user memory): multi-task plans → subagents, fresh context per task, no mid-stream check-ins. The TDD-per-task loop above is the unit of subagent work.

8 Error handling

Recurring discipline across all 24 plans: degrade, don't crash; observe, don't propagate.

FailureTreatment
Validator crash on bad inputConvert to a HarnessRecommendation with category validation, summary "validation check failed". Never block the review pipeline.
Missing skill filelogging.warning + recorded in session JSON. Member proceeds without it.
Malformed frontmatterSame — warn + skip + persist.
Body exceeds capWarn + truncate with explicit marker.
Hook raisesTreated as deny with reason "hook crashed: <ExceptionType>". Logged via logging.exception, never propagated.
Hook times outSame — deny with reason "hook timeout".
Tool returns CONTRADICTEDToolResult.triggers_revision = True; forces a revision turn rather than silently ignoring.
Session lacks new fieldhasattr(session, "tool_call_results") guard. Back-compat without migration.
Schema-shape collisionUse existing _ensure_columns pattern — additive column adds, no migrations.
Hand-edited markdown driftLazy reconcile on every read — markdown is source of truth, sidecar regenerable.
Rule of thumb: every failure mode produces a named entry somewhere observable (ledger row, session JSON, log line). Never a silent skip.

9 Observability (ledger discipline)

Every subsystem writes to server/harness/ledger.py so future tuners can learn from its behavior. This is what enables the meta-learning loop — without it, the project is just code, not a self-improving system.

PatternUse
New column on existing tablevalidation_warnings TEXT DEFAULT '[]', skills_used TEXT — additive via _ensure_columns.
New append-only tablehook_events(session_id, tool_name, action, reason, metadata, ts) — no FK, recordable from any layer.
Per-session JSONRicher detail (full transcripts, missing-skill lists) — round-trips via BoardSession.to_dict().
Eval signal additionObservedSignals.sotb_health_warnings: int = 0 — additive observability; no eval-corpus checker required.
Always compute, even when darksession.disagreement_score always populated even when auto_promote_enabled = False. Telemetry for "would have fired."
The dark-launch + always-compute pair is the calibration engine: ship a behavior cold, watch the signal it would have produced, then flip the flag once the data justifies it.

10 Verification

10.1 Per-task verification

Every task ends with a bash command and its exact expected output:

uv run python -c "from server.harness.skills import list_skills; print([s.name for s in list_skills()])"
# Expected (exact): ['jtbd_interview', 'pricing_research']

10.2 Per-PR verification sweep

  1. Full new test surface (the PR's own tests).
  2. Broader contract suites that touch the changed files.
  3. Manual CLI smoke (uv run python -m server.cli --list-members).
  4. Public-surface invariants (no _-prefix regression, no __all__ regression).

10.4 Risks & mitigations table

Every plan closes with Risk | Likelihood | Impact | Mitigation. These are the failure modes the implementer can't fix in-PR but the operator should know exist — a contract between author and future debuggers.
